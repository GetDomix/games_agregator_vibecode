# Архитектура административных ролей и security-контура Игроскана

Дата: 2026-08-09

## Цель

Превратить текущую административную страницу в защищённый операционный контур с явным разделением владельцев и администраторов. Владелец управляет составом команды сайта; администратор работает с мониторингом и операционными функциями, но не может изменять роли.

## Роли и полномочия

В `users` хранится поле `admin_role` с одним из трёх значений:

- `user` — административного доступа нет;
- `admin` — доступ к мониторингу, пользователям, каталогу, аудиту операционных действий и ручному обновлению игр;
- `owner` — все права администратора и управление ролями команды.

Адреса из `ADMIN_EMAILS` всегда получают эффективную роль `owner`. Это аварийный серверный доступ, который нельзя отозвать через интерфейс. Существующее значение `is_admin=true` при миграции преобразуется в `admin_role=admin`. После переходного периода чтение и запись `is_admin` прекращаются.

Владелец может назначить другому пользователю роли `admin` и `owner`, а также вернуть его в `user`. Обычный администратор не может менять роли. Последнего владельца нельзя понизить. При этой проверке учитываются и владельцы из базы, и неотзываемые владельцы из `ADMIN_EMAILS`. Самопонижение владельца допускается только при наличии другого эффективного владельца. Любое назначение или снятие роли `owner` требует текущий пароль инициатора.

## Backend-архитектура

Проверки доступа выносятся из `AdminController` в два middleware:

- `EnsureAdminRole` допускает `admin` и `owner`;
- `EnsureOwnerRole` допускает только `owner`.

Бизнес-логика разделяется на сервисы:

- `AdminOverviewService` собирает агрегированные метрики и операционное состояние;
- `AdminRoleService` проверяет переходы ролей и выполняет их в транзакции;
- `AdminAuditService` создаёт нормализованные записи аудита без секретов.

Изменение роли блокирует целевого пользователя и строки владельцев через `SELECT ... FOR UPDATE`. Это не позволяет двум параллельным запросам одновременно удалить последнего владельца. После успешной смены роли все токены целевого пользователя отзываются; новый уровень доступа он получает после повторного входа.

Контроллеры отвечают только за валидацию HTTP-входа, вызов сервиса и формирование ответа. SQL аналитики и правила переходов ролей в контроллерах не остаются.

## API

Маршруты для `admin` и `owner`:

- `GET /api/admin/overview` — агрегированные показатели и состояние сервисов;
- `GET /api/admin/users?q=...` — безопасная выборка пользователей без секретов;
- `POST /api/admin/games/{appid}/refresh` — постановка штатного обновления в очередь;
- `GET /api/admin/audit` — пагинированный журнал доступных инициатору действий.

Маршрут только для `owner`:

- `GET /api/admin/team` — полный список пользователей с эффективными ролями `admin` и `owner`;
- `PATCH /api/admin/team/{user}` с `role=user|admin|owner`; поле `current_password` обязательно, если прежняя или новая роль равна `owner`.

Старый маршрут `POST /api/admin/users/{id}/admin` удаляется после перевода интерфейса и тестов. Массовое назначение ролей не добавляется.

Чтение и изменения получают отдельные rate limits. Изменение ролей имеет самый строгий лимит. Проверка роли всегда выполняется backend-ом независимо от отображения элементов интерфейса.

## Интерфейс

Админка разделяется на пять вкладок:

1. «Обзор» — KPI, источники, очередь, доставки и последние ошибки.
2. «Каталог» — проблемные запросы и ручное обновление игры.
3. «Пользователи» — поиск и безопасное состояние аккаунта.
4. «Команда» — только для владельца; список владельцев и администраторов, назначение и отзыв ролей.
5. «Аудит» — пагинированный журнал действий.

Опасные изменения выполняются через отдельное подтверждающее окно. Для изменения роли владельца окно содержит поле текущего пароля, имя цели, прежнюю и новую роли и явное описание последствий. UI не предлагает самопонижение последнего владельца, но окончательное ограничение обеспечивается backend-ом.

## Аудит

Запись содержит:

- инициатора;
- действие;
- тип и идентификатор цели;
- прежнюю и новую роли для ролевых изменений;
- request ID;
- время создания.

В аудит не попадают пароли, access tokens, Telegram chat ID, содержимое исключений и полные HTTP-заголовки. Успешное изменение создаёт запись в той же транзакции. Отказ в изменении роли не создаёт ложную запись об успехе.

Администратор видит операционные действия. Владелец дополнительно видит изменения ролей. Записи аудита не редактируются и не удаляются через API.

## Ошибки

- `401` — пользователь не аутентифицирован;
- `403` — роль не позволяет действие;
- `404` — целевой пользователь или игра отсутствует;
- `422` — недопустимый переход роли, неверный пароль или попытка снять последнего владельца;
- `429` — превышен административный rate limit.

Ответы не раскрывают SQL, stack trace, наличие скрытых учётных записей или секретные конфигурационные значения.

## Security-проверки

Автоматические feature-тесты покрывают:

- все административные endpoints без токена, с `user`, `admin` и `owner`;
- запрет управления ролями для `admin`;
- запрет понижения последнего владельца;
- проверку пароля при назначении и снятии `owner`;
- недопустимые роли, лишние JSON-поля и попытки mass assignment;
- конкурентное понижение владельцев;
- отзыв токенов после смены роли;
- IDOR и перебор пользовательских ID;
- SQL-инъекционные и wildcard-abuse строки в поиске;
- отсутствие пароля, токенов, Telegram ID и других закрытых полей в JSON;
- rate limiting административных изменений;
- корректное создание audit-записей;
- аварийный owner-доступ через `ADMIN_EMAILS`;
- миграцию существующих `is_admin` значений.

Дополнительно выполняется обзор trust boundaries: публичный API, Sanctum bearer tokens, внутренний Telegram API, PostgreSQL, очередь и внешние источники цен. Результат является инженерным security review и набором регрессионных тестов, а не формальным сертификатом аудита или полноценным внешним pentest.

## Критерии готовности

- роли `user`, `admin`, `owner` работают на backend и frontend;
- только владелец может менять роли;
- невозможно удалить последнего владельца даже конкурирующими запросами;
- изменение owner-роли требует пароль;
- смена роли отзывает токены цели;
- административные маршруты защищены middleware и rate limits;
- аудит не содержит секретов;
- security-набор, существующие backend-тесты, frontend lint и production build проходят успешно.
